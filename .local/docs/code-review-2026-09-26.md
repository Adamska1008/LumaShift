## R1：全局快捷键注销的跨线程锁等待

显示工作线程在配置保存、开始录入快捷键时调用 `unregister_all()`。锁定的 `tauri-plugin-global-shortcut 2.3.2` 在持有快捷键表 MutexGuard 时投递主线程注销任务，并同步等待其结果。

Windows 的 `WM_HOTKEY` 回调在主线程同步进入该插件的事件处理器，而处理器也要取得同一个 mutex。如果热键消息先于注销任务被主线程处理，主线程等待 worker 持有的锁，worker 等待主线程执行任务，构成循环等待。界面、后续显示写入以及恢复退出均可能卡住。

锁定依赖源码证据（Cargo registry 中对应版本）：

- `tauri-plugin-global-shortcut-2.3.2/src/lib.rs:220–225`：持锁调用注销；`75–84`：投递主线程后 `recv()`；`416–418`：热键回调取得同一把锁。
- `global-hotkey-0.8.0/src/platform_impl/windows/mod.rs:146–155` 与 `src/lib.rs:126–128`：主线程窗口消息同步执行回调。
- `tauri-runtime-wry-2.11.4/src/lib.rs:235–253`：非主线程发事件，主线程调用则直接执行。

审查依据为项目与依赖的完整调用链，以及不接触系统快捷键的两线程调度模型；没有故意让原生程序卡死。发生频率未测量。

**建议**：把完整注册/注销事务放在主线程上执行；worker 在未持插件锁时等待结果。备选是修正依赖批量注销中的持锁等待，不能仅把单个底层调用放到主线程。还需处理录入开始、失败回滚等所有 `unregister_all()` 路径。

**回归**：用可控主线程执行队列，让已排队的热键回调与注销交错，确认两者都完成，退出恢复仍能处理。

## R2：部分恢复失败没有进入受限恢复状态

`restore_record()` 按顺序恢复 Gamma 与多个硬件值。若前面的项目成功、后面的项目失败，`restore()` 在 `?` 处返回，未清除 `expected_gamma` 和 `last_hardware`。关闭效果、原始对比、切换屏幕和刷新等调用方也在 `?` 处返回，未禁用效果或置 `recovery_pending`。

例如 Gamma、brightness 已恢复而 contrast 失败，之后拖动 Gamma 仍可执行新写入；brightness 的缓存却仍记录旧效果值，从而被跳过。错误提示出现了，但状态并未阻止进一步写屏，界面与物理状态可能不一致。

**建议**：恢复失败统一禁用效果、失效应用缓存、保留原始记录并设置待恢复；恢复完成前拒绝新应用。

**回归**：假显示后端让最后一个恢复项失败，覆盖关闭、对比、刷新和切屏，断言后续 Preview 不再写屏、恢复记录仍在。

## R3：前端队列使后端合并失效

`flushPreview()` 每次捕获一份 profile，追加到 `previewInFlight.then(...)`。每份请求都等待上一份 IPC 返回，后端几乎没有同时等待的 Preview 可合并。若一次 Gamma/DDC 操作比 90 ms 发送间隔慢，旧值持续堆积在前端链里；关闭、切换与保存也先等待这条链完成。

从实际源码提取函数的 mock IPC 复现：首个请求挂起时产生六份调整，然后关闭，最终处理序列是 `1.1 → 1.2 → 1.3 → 1.4 → 1.5 → 1.6 → off`，没有丢弃任何过时中间值。

**建议**：一个执行中请求，加一个可被覆盖的最新待发值；完成当前请求后再取最新值。关闭/恢复是队列边界，应丢弃不再需要的待发预览，等待当前写入完成后恢复。

**回归**：延迟的 IPC 下拖动数百次，待发数量应有固定上限；关闭等待时间不随此前拖动时长增长。

## R4：保存回执覆盖较新的本地草稿

`applySnapshot()` 对 `saved` 无条件替换 `currentDraft`。保存 1.2 的 IPC 未完成时继续拖到 1.5，旧保存回执先将界面重置为 1.2；随后 1.5 的 Preview 成功，但 `preview` 分支不更新本地草稿。

实际函数 mock 结果：`UI Gamma = 1.2`，`backend draft Gamma = 1.5`，`saved config Gamma = 1.2`。因此界面还会显示已保存、禁用保存按钮，而屏幕使用另一个值。

**建议**：用本地编辑序号/预设身份关联保存请求和回执。更新已保存基线时，保留请求发出之后的编辑。

**回归**：保存挂起期间继续编辑，分别交换保存响应与预览完成顺序，检查可见值、dirty 标记与后台一致。

## R5：聚焦数值框跨预设提交

`Range` 聚焦时跳过外部 value 更新；父组件按字段名复用该组件，预设切换不会重建输入状态。全局快捷键可在输入仍聚焦时切换预设，而 `onBlur` 使用的是新预设的回调。

从实际 Range 函数提取并模拟 hooks：桌面输入 `1.9` 未提交，切到 Gamma 为 `1.2` 的塔科夫后，输入仍为 `1.9`；失焦产生 `{ id: "tarkov", value: 1.9 }`，修改了另一预设。

浏览器演示监听器主动跳过 input 中的快捷键，不能覆盖原生全局键的这条路径。

**建议**：输入编辑状态关联预设/显示器身份；身份变化时明确取消或提交给旧上下文，不能让旧输入通过新回调提交。按预设 ID 为 Range 建 key 是一种实现方式，但仍需验证 unmount/blur 顺序。

**回归**：聚焦输入、未提交、全局切预设、失焦，新预设应保持原值。

## R6：自动应用转移目标显示器

启动先 `ensure_display()`，找不到保存的目标 B 就改成当前第一台 A；随后 `apply_last_on_start` 检查未验证原目标是否仍存在，直接开启效果。

条件：已保存 B、当前只有 A、自动应用开启、没有恢复记录、安全启动未启用，且预设有非中性 Gamma 或 A 可用的硬件项。若启动到托盘也开启，错误目标上的调整会在隐藏窗口状态下发生。

**建议**：自动应用前确认原保存目标仍存在。可以为界面选择备用屏，但暂停自动应用并提示用户选择目标。

**回归**：B 缺席时写入次数为零；B 存在时只应用 B。

## R7：快捷键冲突阻止无关配置保存

每次 `save_config()` 都调用 `shortcuts::replace()`，即使只改主题、语言或 Gamma 预设内容。若启动时 F6 被其他程序占用，应用能启动并显示冲突，但以上保存都会在重新注册失败后被拒绝。这也不必要地增加 R1 的触发机会。

**建议**：仅绑定集合变化时更新注册。保存无关配置时保留既有注册状态和冲突提示；注册失败回滚仅限实际变化的绑定。

**回归**：假注册器设置 F6 冲突，主题和调色仍可保存；改成冲突键时仍应拒绝绑定变更。

## R8：相同恢复基线重复同步刷盘

每次 `apply_inner()` 都调用 journal，即使本次基线没有变化、甚至没有硬件写入。`storage.rs:93–117` 每次重新序列化、写临时文件、`sync_all()` 再 `MoveFileExW(...WRITE_THROUGH)`；全部位于写屏之前的单 worker 上。

前端目标间隔为 90 ms，即最多约 11 次预览/秒；实际处理频率受后端耗时限制。未取得可靠的磁盘延迟基准，不能据此声称具体毫秒耗时或当前磁盘已成为瓶颈。可确定这些相同内容的同步写入是不必要的。

**建议**：仅首次真实修改、新增原始硬件项、gamma_changed 首次置 true 时，在写屏前持久化。必须单独跟踪磁盘记录是否存在：原始对比会删除记录但保留内存 session，切回当前时仍需要先重新落盘。

**回归**：存储假实现计数，同一会话的 100 次 Gamma 预览只首次持久化；新增硬件项、对比后重新应用仍验证日志先于硬件写入。

## R9：周期检查依赖队列完全空闲

拓扑/HDR 和外部 Gamma 检查放在 `recv_timeout(4s)` 的 Timeout 分支。每个新请求都会重置等待，持续滑动时检查可无限推迟，继续使用旧模式和句柄判断。

**建议**：用固定 `Instant` 截止时间调度，处理请求后检查是否到期；不能让新请求重置下一次检查时间。

**回归**：每 100 ms 注入请求超过八秒，中途改变拓扑，检查仍应按期执行。

## R10：托盘动作过早解析

托盘回调读取 Shared 快照，立即把 Toggle 解析成具体布尔值，Next 解析成具体预设 ID。慢 DDC 占用 worker 时，连续两次 Toggle 可都得到 `true`，连续两次 Next 可都得到 B，实际只前进一次。

**建议**：像全局键一样发送动作意图，在 worker 消费时按实时状态解析，不在 UI 回调时解析。

**回归**：延迟 worker，两次 Toggle 回到初态；三预设下两次 Next 前进两项。

## R11：恢复旧会话失败的托盘退出反馈

有旧恢复记录、原显示器未连接、窗口隐藏时，Quit 分支的 `Recover?` 提前返回，跳过后续显示/聚焦窗口的错误处理。错误只发送给隐藏页面，进程继续常驻，用户看不到原因及保留记录退出入口。

**建议**：将旧会话恢复与当前会话恢复纳入同一个退出失败处理，统一唤出窗口，保留记录并反馈恢复错误。

**回归**：假恢复存储和断开设备，Quit 不退出、记录保留、窗口被显示。

## 结构与测试建议

现有曲线、协议解析和持久化模块已有分离；无需为优化而更换技术栈。主要缺口是 Engine 同时依赖具体 Win32 Display、Tauri AppHandle、快捷键插件和存储，使最重要的失败时序难以隔离测试。

1. 为显示读写、存储、快捷键注册和窗口通知提供小接口；先覆盖失败注入、线程顺序和恢复状态，而非引入通用服务框架。
2. 用明确会话状态表达 Off、Applying、Comparing、RecoveryRequired，减少 enabled/comparing/recovery_pending 组合不一致。
3. 将前端调度与编辑状态从 App 中提取，增加延迟 IPC、保存期间编辑、原生全局切换场景的回归测试。浏览器模拟立即返回，不能替代这些测试。
4. 减少 Preview 携带的完整配置快照、比较新增状态后再通知等可在测量后进行；目前没有数据证明需要重做渲染或曲线算法。
